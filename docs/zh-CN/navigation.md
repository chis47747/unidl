# 返回（Back）与逐级导航

[English](../navigation.md) | [简体中文](navigation.md)

## 核心规则

**返回（Back）会回到打开当前步骤的紧邻上一级页面。** 它不是直达服务主页或平台列表的快捷方式。该规则统一适用于键盘返回、鼠标点击返回、搜索结果、目录浏览、轨道/源选择、下载成功、下载失败以及保存命令/导出结果页面。

这里的“页面”指逻辑上的交互步骤，未必对应单独的 Textual Screen。搜索结果、季列表和集列表完全可以共用同一个 `FlowScreen`，但按返回（Back）时仍必须逐级经过每一个页面。应保持所属生成器与页面状态存活，而不是重建整个服务会话。

**只有当服务主页确实是上一级页面时**，它才是合法的返回目标（例如从服务主页打开的 URL/搜索输入框按返回）。在服务主页自身按返回（Back）会离开该服务，回到平台列表。切勿凭空补出从未展示过的季、片源或轨道页面——通过直链进入的作品，其父级页面数量自然可能少于通过搜索进入的作品。

## 预期返回目标

| 当前页面 / 操作 | 返回（Back）目标 |
|---|---|
| 从选季界面打开的集数列表 | 该选季界面，而不是搜索结果或服务主页。 |
| 从搜索结果打开的选季界面 | 该搜索结果页，而不是搜索输入框。 |
| 搜索结果页 | 发起本次搜索的搜索输入框页面。 |
| 从选集界面打开的音频/源选择页 | 紧邻的选集或源选择页，每次只退一级。 |
| 已完成或已失败的交付/结果页 | 紧邻的前一个活跃选择/输入页。任务成败不改变父级目标。 |
| 保存命令、导出文件或仅列轨道结果页 | 发起该操作的选择/输入页。 |
| 设置、章节、附件、歌词或任务详情弹窗 | 仅关闭该浮层并露出原页面，不连带触发底层页面返回。 |
| 从服务主页打开的搜索/URL 输入框 | 服务主页（此处它确实是直接父级）。 |

例如，一个依次展示全部选择步骤的服务，其返回链路应当是：

```text
delivery/result → audio/source → episodes → seasons
                → search results → search input → service home → platform list
```

恢复上一级页面时，应保留已有的光标位置、已勾选集数、搜索文本以及已加载的结果列表。返回（Back）绝不能重新发起 API 搜索或下载、自动重试失败标题，或丢弃已经成功的有效输出。

先前发生过的 manifest、许可证或下载失败不会在返回链路中额外插入一个错误摘要页。回到服务主页后，哪怕当前会话队列里仍有失败任务，再按一次返回（Back）也会直接离开服务回到主界面。同时保留这些任务的结果与日志，不要为了放行导航而清空失败记录。若某个流程确实因错误中止且用户尚未在服务主页显式按返回，错误信息仍会保持可见直到用户主动离开。

## 流程归属与异常透传

委托子流程时请使用 `yield from`。它会同时把正常应答**和**异常透传给当前活跃的子流程。子流程可以捕获 `Back` 并重新 yield 它自己的父级页面；外层流程不得重复吞掉第二次返回或再多跳一级。未处理的 `Back` 应当精准向上冒泡一层至直接持有者。

共用的 `Service._did_anything()` 搜索包装器仅统计子流程是否产出了询问或播放项，不会改变上述委托规则。它同样会把异常与应答透传给子流程，并在销毁时关闭子流程。服务自定义的 `home()`、直接 `yield from` 委托或现有的 `_did_anything()` 重写仍保有完全控制权，Core 不会在外层额外套一层导航包装。

切勿仅用 `flow.send(answer)` 手写代理：一旦在代理的 `yield` 处抛入 `Back`，子流程会在其恢复处理逻辑运行之前就被直接关闭。如果确有必要手写代理，必须同时用 `flow.throw(exc)` 透传异常。遇到 `GeneratorExit` 时应将其视为清理终止信号：关闭子流程并释放资源，不要再 yield 新页面。

## 保持最近父级存活

每个页面都应由自己负责从它所打开的子流程中恢复。将页面的 `yield` 放在子流程恢复代码块之外，这样**在当前页面**按返回（Back）即可离开它，而从更深层子流程按返回时则会恢复到它：

```python
def browse(ctx, page, visit):
    while True:
        selected = yield page
        # Update page.cursor/preselected here when appropriate.
        try:
            yield from visit(selected)
        except Back:
            continue  # Child closed: restore this immediate parent.
        except RuntimeError as exc:
            ctx.problem("Could not finish that", str(exc))
            continue  # Recoverable child failure: same parent, not service home.
        if not ctx.interactive:
            return    # Headless rules must not create an endless prompt loop.
```

服务预期内的网络或准备阶段错误应在同一个最近父级处捕获。不要用过于宽泛的 `except` 吞掉编程错误或 `Quit`。一旦异常逃逸并终止了生成器，外层页面就再也无法恢复已经丢失的调用栈。服务主页的错误处理仅作为最后的兜底边界，而不是搜索、manifest 或下载失败后的常规导航机制。

下载成功与下载失败必须保留完全一致的返回目标。在共用的交付驱动器中，已完成任务的 `Back` 会直接抛入服务的 `yield ctx.emit(...)` 处，因此要保持承载该 `emit` 的选择器或输入页存活。该信号同样涵盖了关闭已完成结果页的场景，切勿将其解读成跳过所有浏览层级直接退回顶层。

## 运行中的下载、批量任务与退出（Quit）

任务运行期间按返回（Back），依然会先按既有规则触发停止或录制收尾，再退回上一级页面；本导航规则不会移除取消、检查点清理或直播录制收尾逻辑。相关生命周期规则请参阅 [cancelling.md](cancelling.md)。

批量任务中某个中间标题的成功或失败不会触发导航事件，而是按既有批量策略继续执行。当最后一个标题结束或用户显式停止整批任务后，返回到拥有该批次/交付的活跃页面，而不是直接跳回服务主页。显式停止后，剩余标题保持未开始状态。历史/详情弹窗始终只关闭自身。

退出（Quit）不是返回（Back）。它遵循应用既有的退出与现场保留策略，绝不会重新打开父级选择器，也不会额外触发直播录制收尾。

## 验证要点

测试逐级返回时应从真实入口贯通验证，而不只是孤立测试 `service.search()` 或 `open_url()`：

- 分别从通用服务主页、自定义服务主页以及直链入口进入。
- 依次走过实际展示的搜索结果、季列表、集数列表以及任意源/音频选择页。
- 覆盖成功下载、准备/下载失败、仅保存命令/导出结果以及中途停止的批量任务，确认返回（Back）始终回到同一个真实父级。
- 验证光标与勾选项得以保留，且不会重复发起服务方 API 请求。
- 启用服务现有的导航重写逻辑后再复测一遍，确保一次返回绝不会产生两级跳转。
- 全面核对鼠标返回、键盘返回、弹窗关闭、退出（Quit）及生成器清理行为。
