# 纯音频服务

[English](../audio.md) | [简体中文](audio.md)

电台和播客并不是“少了画面的视频”。它们没有画质阶梯可供排序，原生下载器在选中视频轨道时会直接拒绝 `--audio-format`，而且输出文件需要视频用不上的 ID3 标签。如果把音频当成视频的特例来凑合，结果只会在各个环节半吊子运行。

因此，音频在模型中是与视频类型并列的独立标题类型（`TitleKind`），而不是挂在视频类型上的标志位：

| 类型 | 含义 | 是否直播 |
|------|------|----------|
| `TRACK` | 电台节目或播客单集 | 否 |
| `STATION` | 直播电台 | 是 |

除了没有画面外，`STATION` 在其他所有方面都等同于电视频道，因此 `STATION.is_live` 为真，与 `CHANNEL.is_live` 一致。

## 服务侧无需额外声明

服务只需设置正确的类型，其余属性均由 `Playback.__post_init__` 自动推导：

```python
Title(kind=TitleKind.TRACK, name="Desert Island Discs", artist="BBC Radio 4", ...)
# -> playback.audio_only is True
# -> playback.audio_tags is filled in from the title
```

`is_live` 同样由标题类型推导。这两个标记在此处只会从类型自动**开启**，因此服务依然可以为本身不隐含该特性的类型显式启用它们——例如以纯音频模式录制直播电视频道。

## 引擎的后续处理

1. **只选音频轨道。** 直接不设置视频选择器，而不是先选再过滤丢弃：既没有清晰度阶梯需要排序，原生下载器也会在选中视频轨时直接拒绝 `--audio-format`。若直链 MP3/AAC 在探测时将内嵌封面报告为 `video` 轨道，也会在此边界规整回 `audio`。字幕同样不会选中，因为 MP3 无法承载字幕，选中它只会多出一个零散文件并让轨道列表显得混乱。
2. **按需重新编码。** 读取轨道设置中的 `audio_format`，对包含画面的标题忽略该设置。
3. **写入 ID3 标签。** 通过外挂 JSON 文件传递——既因为这是原生下载器提供的接口，也因为导出的命令之后重放时必须依然有效；如果标签只留在内存里，导出命令就无法复现。
4. **对直播音频去掉 `--live-pipe-mux`。** 原生下载器不允许它与 `--audio-format` 同时使用，而且单条音轨本身也没必要走管道混流。

## TUI 展示

在交互式选轨时，纯音频标题采用双栏界面：左侧固定显示专辑封面和已知的 ID3 字段，右侧展示常规的轨道列表、筛选器与选择控件。进入实际音频下载后，同一份预览卡片会移至交付界面右侧，进度、解密和混流状态留在左侧。视频点播与直播录制仍保持常规的全宽交付布局。封面加载采用尽力而为策略并在 UI 线程之外异步执行，封面 URL 缺失或过期绝不会阻塞选轨或下载。

在支持 Kitty/Sixel 协议的终端上，预览使用终端原生图像协议保留源像素；普通 ANSI 终端（包括 macOS 自带终端）则使用 36×36 半字符点阵，以保证通用显示效果——该尺寸下封面上的小字可能会变得模糊，因为终端字符格本身无法承载浏览器级的图像细节。启动阶段不会发送终端能力探测序列。

## 格式列表不在此处硬编码

`audio_format` 提供的可选值完全取决于当前 UniDL 构建版本的实际能力，直接从原生解析器读取。目前可用的转换格式包括 320 Kbps 的 `mp3`、`flac`、封装在 M4A 容器中的 `alac`，以及表示“保留原轨、不重编码”的 `source`。

当原生引擎新增对某种格式（如 FLAC）的支持时，界面选项会自动出现，无需改动上层代码。更重要的是，当前环境无法生效的选项绝不会展示；如果某个支持该格式的构建版本在 `settings.json` 中留下了对应配置值，回退到旧构建时会记录一条日志并自动降级为保留原轨，而不会在最后一步才报错失败。

当服务本身已经提供 MP3 时，建议选择 `source`，避免无谓的二次编码并保留原始音频质量。

## 标签

标签值全部来源于标题对象，且只写入已知项——空标签比缺少标签更糟糕，因为播放器通常会把它显示为空白字段，而不是自动回退：

| 标签 | 来源字段 |
|------|----------|
| `title` | `episode_name`，否则取 `name` |
| `artist`、`album_artist` | `artist`，否则取 `channel` |
| `album` | `album`，否则取节目名称 |
| `date` | `year`，否则取播出日期 |
| `track` | `track_number`，否则取 `episode` |
| `genre`、`publisher`、`comment` | `genre`、`publisher`、`synopsis` |
| `cover` | `cover_url`，封装为 `{"url": ...}` |

这些字段直接定义在 `Title` 上而不是塞进 `data`，因为 `data` 是服务的私有载荷、核心层不得读取，而这些字段恰恰是核心层必须读取的数据。

如果服务的片库接口提供了通用 `Title` 模型未涵盖的更丰富信息，服务也可以直接填充 `Playback.audio_tags` 字典，包括 `album_artist`、`track/total`、`disc/total`、`composer`、`copyright`、`ISRC` 以及封面请求头。该字典会原样存入 JSON manifest，确保无论是立即执行还是导出后稍后重放，原生下载器拿到的元数据完全一致。即使可选的元数据补充请求失败，基于简介提取的字段以及基础的标题/艺人/专辑信息依然可用。

## 验证方法

项目中有针对性的冒烟测试，专门覆盖音频元数据模型与原生下载契约，运行过程既不会访问外部服务，也不会读取账号状态。
