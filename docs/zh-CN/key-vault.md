# Key Vault（密钥库）

[English](../key-vault.md) | [简体中文](key-vault.md)

密钥库是一组按顺序排列的内容密钥存储后端。在未配置 `key_vaults` 时，默认仅包含位于 `paths.keys_db` 的单个本地 SQLite 数据库；你也可以额外配置多个 SQLite 文件和 HTTP API 密钥库。**设置 → DRM 与密钥库**负责管理各后端的定义和启用状态，其中的**密钥库策略**面板用于精确指定哪些已启用的后端参与查询、搜索和写入。

## 为什么值得配置

密钥的复用频率远高于大多数人的预期。单个标题通常会为**所有加密轨道签发同一个 KID**——涵盖全部视频清晰度阶梯和所有音频流。因此，首次获取到的密钥往往足以覆盖整个标题，再次下载时完全不需要重新请求许可证。

这一特点在单次运行内同样成立，也就是说，即使你还没有重复下载过同一内容，密钥库也已经开始发挥作用了。

## 设计思路与借鉴来源

以下设计借鉴自 unshackle（`unshackle/core/vault.py`、`unshackle/vaults/SQLite.py`、`docs/guide/vaults.md`）：

- **按 KID 匹配，绝不按 PSSH 匹配。**同一内容在不同请求间可能返回不同的 PSSH box，部分服务甚至直接返回 CENC 头而非 PSSH box；而 KID 只有在媒体本身变化时才会改变。
- KID 与密钥均以**32 位小写十六进制字符（不含连字符）**存储，并使用 `COLLATE NOCASE` 进行比较。
- **全零密钥不是有效密钥**：查询时跳过，写入时拒绝，避免占位符掩盖真实密钥。
- 使用 `UNIQUE(kid, key)` 约束，重复写入会直接忽略，而不会产生冗余记录。
- SQLite 启用 WAL 模式、`synchronous=NORMAL`、30 秒 busy timeout 以及每线程独立连接，使 UI 线程与下载工作线程能够安全共享同一个数据库文件。

以下设计则是有意**没有**沿用的部分：unshackle 为每个服务按服务标签单独建表，而 unidl 使用单张表并通过 `service` 列区分来源：

- 全局查询“这个 KID 来自哪个标题”只需一次走索引的查询，而不必遍历 `sqlite_master` 逐表扫描——unshackle 在其 `kv search` 文档中也提到了这一局限。
- 密钥来源信息记录到每一行而非整张表，包括标题、来源、CDM 和时间戳。
- SQL 语句中绝不拼接表名（unshackle 源码中恰恰有三处针对此问题的 `TODO: SQL injection risk` 注释）。

## 数据库表结构

```sql
CREATE TABLE keys (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    kid        TEXT NOT NULL COLLATE NOCASE,
    key        TEXT NOT NULL COLLATE NOCASE,
    service    TEXT NOT NULL COLLATE NOCASE,
    title      TEXT,
    pssh       TEXT,
    source     TEXT NOT NULL DEFAULT 'license',
    cdm        TEXT,
    origin     TEXT,
    created_at TEXT NOT NULL,
    UNIQUE(kid, key)
);
CREATE INDEX keys_kid_idx     ON keys(kid);
CREATE INDEX keys_service_idx ON keys(service);
CREATE INDEX keys_title_idx   ON keys(title);
```

| 列名 | 含义 |
|------|------|
| `kid`、`key` | 均为 32 位小写十六进制字符串 |
| `service` | 服务 ID；手动录入且刻意不指定归属服务时为 `unknown` |
| `title` | 保存名称，用于将密钥回溯到具体标题 |
| `pssh` | 已知时记录；仅供参考，绝不参与匹配 |
| `source` | `license`（从服务许可证获取）、`vault`（远程回填）或 `manual`（手动添加） |
| `cdm` | 获取该密钥时所使用的已配置设备 |
| `origin` | 显式写入方，例如手动录入时为 `tui` |

## 在流水线中的位置

```
解析 manifest   ->  获取已知 KID
                ->  查询密钥库
                    所有 KID 全部命中？ ->  直接使用，跳过许可证请求
                    存在缺失 KID？      ->  仅对未命中 KID 请求许可证，合并后写入密钥库
                ->  共享输出轨道选择
```

解析必须排在最前面，因为只有解析 manifest 后才能得知 KID。出于同样的原因，`tui/session.py:_process` 的执行顺序是 `load_tracks`、`resolve_keys`，随后才是输出轨道选择。默认情况下，密钥库查询与许可证清单覆盖完整解析出的加密轨道阶梯；若服务启用了**最终选轨后获取许可**，则仅覆盖最终选中的加密轨道。

只有当密钥库返回完整密钥集合时，才会跳过许可证交换。若仅为部分命中，命中结果会保留在当前播放上下文中，同时由服务自身的许可证路径获取缺失的 KID，随后由核心层按 KID 合并两组结果。这一点对 PlayReady 尤为关键，因为单个 PSSH/WRM 头通常只能换回其对应的单个密钥：已被密钥库覆盖的 PlayReady 头会被跳过，而携带其他 KID 的头仍会发送到该服务的许可证端点。当 manifest 可能隐藏额外 KID（例如 HLS 媒体播放列表或 Widevine v1 PSSH）时，初始化数据探测会在最终判定“是否全部命中缓存”之前执行。

每次被查询的密钥库都会在会话日志中写入独立记录，标明其名称以及属于本地还是远程。日志结果会明确区分完全命中、部分命中（附缺失数量）、无匹配密钥以及查询失败/不可用。其中的数量统计针对的是“查询该密钥库时尚未解决的 KID”，而不是整个标题的全部 KID。已停用、未被选中或无需继续查询的密钥库不会被访问，也不会被记作未命中。最终的全命中汇总仅列出实际提供了密钥的密钥库。这项日志报告不会增加额外请求，也不会改变查询顺序、本地回填或许可证回退行为。

当服务声明 `USES.drm = self` 且启用了本地或远程查询时，同样遵循上述顺序。在调用服务自有的 `get_keys()` 之前，Core 会直接使用已解析清单中存在的 KID，执行相同的“先本地、后远程”查询。若全部命中，则跳过该服务的许可证请求；若部分命中，则将已有密钥写入 DRM 上下文，再与服务返回的密钥合并。服务依然全权负责自身会话、challenge 构造与许可证端点——密钥库绝不会充当替代的传输通道。关闭远程开关时，Core 仅查询允许访问的本地密钥库。如果这类服务只有在运行自有解析器时才能发现按轨道分布的额外 PSSH/KID，则会继续走该解析器及服务许可证路径，Core 绝不会代其猜测纯 KID 请求。

服务设置页中的**授权与密钥库**分区控制本地/远程查询、自动写入以及目标列表。未保存服务级覆盖项时，每一行都会继承全局**DRM 与密钥库 → 密钥库策略**中的值。界面会展示当前生效值及其来源；按 `r` 可清除服务级覆盖。显式关闭或显式将目标设为空列表都属于有效覆盖，而不是“未设置”。启用**最终选轨后获取许可**后，只有最终选中的加密轨道所对应的 KID/PSSH 会参与密钥库查询或发证，manifest 中未选中的清晰度阶梯会被忽略。

查询时优先匹配同服务记录，未命中再回退到任意服务。实践中 KID 具有全局唯一性，因此在一个服务名下导入的密钥同样可以用于另一个服务。

## 查看与搜索

在界面中按 `/`，输入 KID、`kid:key` 密钥对或标题片段即可搜索。结果会显示所属服务、标题、来源和日期；按 `ctrl+y` 可复制该密钥对。

**搜索密钥库**是独立于自动下载策略之外的主屏搜索多选项。默认仅勾选本地 SQLite 密钥库，确保本地匹配即时响应且完全离线。清空选择则会关闭密钥搜索。远程后端只有在 YAML 配置中显式声明 `searchable: true` 且适配器具备足够信息以安全执行搜索时，才会出现在该设置中。

当输入精确 KID 且至少有一个已选中的远程后端支持搜索时，**搜索远程密钥库**会排在结果列表第一位。输入过程中不会触发任何网络请求。选中该项后，若仅启用了一个远程后端则直接查询；若有多个，则会弹出单选列表让你指定目标后端。支持按服务区分的 HTTP 密钥库会在首项提供**全部支持的平台**，随后列出其声明的各个平台。选择单个平台时，对每个候选 KID 仅发送该平台对应的 `GetKey` 请求；选择**全部**则会按有限的 `supported_services` 列表依次尝试，并在首次命中时停止。查询结果会展示在界面中供复制，但不会静默写入本地数据库。

### 添加一个或多个密钥

在同一个搜索界面中，点击**添加密钥**或按 `ctrl+n` 即可打开添加页面；也可以通过命令面板选择**向密钥库添加密钥**。若从某个服务内部打开，该服务会自动预选；若从全局界面打开，可输入平台名或服务 ID，从实时筛选出的结果中选择。输入的搜索词会保留显示；编辑或删除已选 ID 即可清除并立即重选其他服务。界面最多仅挂载前 8 条匹配项，而不是渲染包含 150 个服务的下拉框。

宽终端下，“服务”与可选的“标题”字段并排显示；窄终端下则纵向堆叠。选定服务后，候选项列表会自动折叠，直到你再次修改搜索词。密钥编辑区独立滚动，底部的目标列表与操作行始终保持可见。操作按钮采用紧凑单行布局；确认前校验错误与冲突详情会自动滚动到视野内。

编辑区支持每行一对 `KID:key`，同时也兼容直接粘贴的 `--key KID:key` 参数、JSON 或命令行中包含的多组密钥对、带连字符的 UUID 形式 KID、大写十六进制字符以及全角冒号。空行会被忽略。其余每一行都必须能正确解析，左右两侧均须归一化为 32 位十六进制字符；全零密钥会被拒绝，完全相同的密钥对会自动去重，同一批次中若同一 KID 对应两个不同密钥则会报错。整批内容必须全部通过校验后，才会执行任何写入。

保存前，点击**选择密钥库**可多选所有可写的本地与远程后端。初始勾选状态来自**接收获得密钥的密钥库**；当**使用远程密钥库**关闭时，远程目标默认不勾选。该页面属于单次显式覆盖，因此在这里主动勾选远程目标即可授权本次批次上传，而不会修改全局自动播放策略。

每个选中的 SQLite 文件都会在单个事务中写入整批密钥。已存在的相同密钥对会记作已存储（`already stored`）。若某个 KID 已映射到不同的密钥，则判定为冲突：首次提交不会写入任何数据，并会指明发生冲突的数据库；只有显式点击**替换冲突并添加**，才会移除该数据库中的冲突记录并提交新批次。事务原子性以单个数据库为单位，不跨越互不相关的文件或 HTTP 服务器。各目标相互独立：某一个目标失败不会回滚其他已成功写入的目标，结果摘要会列出每个目标的处理情况且不打印完整密钥对。配置了 `no_push: true` 的后端会标记为只读，无法选作写入目标。

命令行用法：

```bash
unidl keys                                          # 按服务汇总
unidl keys 96a9ef1af1094578974d4c09ef8fcecc         # 查询单个 KID
unidl keys 96a9ef... --service example
```

## API

```python
from unidl.core.vault import KeyVault

vault = KeyVault(config.paths.keys_db)

vault.add("example", kid, key, title="Show.S01E01", source="license")
vault.add_pairs("example", ["kid:key", ...], title="Show.S01E01")
preview = vault.preview_pairs(["kid:key", ...])
result = vault.add_many(
    "example", ["kid:key", ...], title="Show.S01E01", source="manual"
)

vault.get_key(kid, "example")              # str | None
vault.get_keys([kid, ...], "example")     # dict，仅包含命中的项
vault.find("Big.Brother")              # 按 KID、kid:key 或标题文本搜索
vault.by_service("example")
vault.stats()
```

辅助函数：`normalize_hex()` 支持带连字符、大写及带引号格式；`split_pair()` 用于拆分 `kid:key`；`is_null_key()` 用于识别全零密钥。

## 关闭密钥复用

密钥复用的确是密钥库的核心价值，但也必须能随时关闭——否则你就无法让某次运行真正请求许可证服务器。

统一的**密钥库策略**面板包含两个总安全开关和四个独立的远程操作开关：

- **使用本地密钥库** — 默认开启
- **使用远程密钥库** — 默认关闭
- **允许从主页搜索远程 KID** — 默认开启；仅在显式触发时执行，输入期间绝不联网，且需要选中支持搜索的后端
- **允许手动添加密钥到远程库** — 默认开启
- **将许可证获取的密钥保存到远程密钥库** — 默认开启
- **获取许可证前检查远程密钥库** — 默认开启

同一面板中的三个目标选择器用于进一步细化上述开关的范围并控制搜索目标：

- **用于查找密钥的密钥库** — 默认包含全部已配置后端
- **接收获得密钥的密钥库** — 默认包含全部可写后端
- **搜索密钥库** — 默认仅包含本地后端；远程搜索始终需要显式点击触发

选择**全部可用**意味着写入所有已启用、可写且受远程安全开关允许的目标，效果等同于逐一勾选这些密钥库，绝不表示“不选任何目标”。已停用和只读的密钥库仍会被排除；显式选择空列表才会关闭写入。该策略同样适用于直播密钥轮换时的写入。修改目标选择不会回传历史密钥，也不会启动密钥库之间的同步。

第一个目标选择器控制自动播放时的密钥查找。第二个控制许可证写入、直播密钥轮换写入，以及远程查得密钥后回填到哪些本地数据库。第三个控制主页搜索涵盖哪些本地数据库，以及允许在主页显式查询哪些声明了搜索能力的远程后端。每个列表都允许为空。四个远程操作开关刻意保持相互独立：例如，你可以在发证前读取远程密钥库但拒绝上传新获取的密钥，或者仅允许手动上传而禁止自动上传。关闭**使用远程密钥库**总开关会覆盖禁用自动查询和自动写入；主页显式搜索拥有独立开关，不会被抹除原有偏好。

保留远程总开关的原因很直接：读取本地文件零开销且完全私密，而访问远程密钥库会产生网络请求，同时也会把你的密钥发送到他人的服务器上。

当读取与写入目标列表均保持默认的 `all` 时，行为如下表所示：

| 开关组合 | 本地读取 | 本地写入 | 发证前远程读取 | 发证后远程写入 |
|---|---|---|---|---|
| 本地开，远程关 *（默认）* | 是 | 是 | 否 | 否 |
| 本地开，远程开；远程查找/写入均开 | 优先 | 是 | 仅本地未命中的 KID | 是 |
| 本地开，远程开；远程查找开/写入关 | 优先 | 是 | 仅本地未命中的 KID | 否 |
| 本地关，远程开；远程查找/写入均开 | 否 | 是 | 是 | 是 |
| 两个总开关或操作开关全关 | 否 | 是 | 否 | 否 |

表中有两点是刻意为之，值得单独说明：

**选定的本地写入仍会执行。**关闭本地复用表示你暂时不信任已有缓存——比如怀疑密钥有误、服务使用同一组 KID 重新加密了内容，或者你正在测试 CDM 与许可证服务器。这并不意味着你不想记录刚刚向许可证服务器换回的新密钥。如果确实不想写入某个数据库，请将它从**接收获得密钥的密钥库**中移除。

**远程总开关同时控制写入。**这种不对称是故意的：不读本地文件只是一种偏好，而向远程服务器推送密钥是对外动作，关闭总开关后就不应发生此类动作。

### 当本地与远程同时开启时

无论 `key_vaults` 中的排列顺序如何，系统始终**先查询本地密钥库**——本地命中零成本且离线，配置文件不应该让每次查询都多走一次网络往返。只有本地未命中的 KID 才会发往网络。

从远程密钥库查回的密钥随后会**复制到已选中的可写本地目标**，因此第二次下载同一标题时完全无需联网。复制方向永远只进不出：查询操作绝不会顺带向外上传任何数据。

`Engine.vault_targets(settings)` 会在自动播放的单一决策点综合这两个安全开关与两个名称列表。如果完全没有设置作用域（例如检查脚本或未传作用域的调用方），默认表现为“仅本地 + 全部本地密钥库”，也就是对“未表态”最安全的解读：没人明确要求时，任何数据都不应离开本机。日志会直接写出实际命中的后端：

```
vault: all 1 keys served from local, no license request
vault: both vault switches are off, going to the licence server
vault local: cached 1 key(s) from the remote vault
```

## 配置多个密钥库

`paths.keys_db` 是默认密钥库；未做额外配置时，它也是唯一的密钥库。在 `unidl.yaml` 中设置 `key_vaults` 会用一组有序列表替换该默认配置：

```yaml
key_vaults:
  - type: sqlite
    name: local
    enabled: true
  - type: sqlite
    name: archive
    path: db/archive.db
  - type: api
    name: shared
    uri: https://keys.example.com
    token: your-token
    no_push: true
```

每个条目都必须拥有大小写不敏感唯一的 `name`，因为两个目标设置保存的正是这个稳定标识。每个新增的 SQLite 条目都应指定各自的 `path`；相对路径会相对于 `unidl.yaml` 所在目录解析，其父目录会以私密权限自动创建。TUI 可以扫描项目 `db/` 目录（若已配置的主目录 `db/` 与其不同，也会一并扫描），找出包含 UniDL `keys` 表的 SQLite 文件，并将它们列为**已发现**（discovered）候选；用户必须显式导入所选文件，它们才会成为已配置密钥库，从而避免备份文件或无关数据库意外参与许可证查询或写入。

系统支持三种后端类型，对应现实中常见的三种接口形态：

| 类型 | 位置 | 接口形态 |
|------|------|----------|
| `sqlite`、`local` | 磁盘文件 | 上文所述的 `KeyVault` |
| `HTTP`、`httpapi` | HTTP 服务 | 单一 URL，在请求体中指定操作：`{"method": "GetKey"\|"InsertKey", "params": {...}, "token": ...}`。`api_mode: query` 则将同样字段放入 GET 查询参数，且需额外提供 `username` |
| `api` | HTTP 服务 | `GET`/`POST {uri}/{service}/{kid}`，使用 `Authorization: Bearer` 鉴权 |

`HTTP` 与 `api` 虽然都基于 HTTP，但仍划分为不同后端，因为二者协议结构不同：前者面向单一 URL 并在请求体中指明操作，后者把服务名和 KID 放在请求路径中。

`HTTP` 后端使用如下 JSON 结构：

```json
{
  "method": "GetKey",
  "params": {"kid": "<kid>", "service": "<service>", "title": null, "session_id": null},
  "token": "<vault-token>"
}
```

写入操作使用 `InsertKey` 并在 `params` 中追加 `key` 字段；`title` 和 `session_id` 保持为显式字段。令牌必须放在包含敏感信息的项目 `unidl.yaml` 中，绝不能写入服务模块、测试夹具、日志或导出的命令。在配置中登记后端只是让它可用；读写是否真正发往该后端，由全局**使用远程密钥库**开关控制。如果后端声明了 `supported_services`，unidl 只会映射已配置的 `service_map` 别名，并跳过不受支持的本地服务 ID，不会将它们发送给服务器。

已配置的远程端点可以提供有限的支持服务标签列表及可选别名。UniDL 只会发送该后端显式声明的标签，不会猜测或向网络发送不受支持的本地服务 ID。请将此列表保留在私有配置中，不要写入公开文档。

端点还可以声明 `searchable: true`。这不会导致输入 KID 时自动发起网络请求；它仅使该后端可在**搜索密钥库**中被勾选，并启用结果行中的显式远程搜索操作。

- 读取按顺序采纳首个返回的密钥，本地始终优先于远程。
- 写入会发往所有已选中、可写且未设置 `no_push` 的密钥库。
- 发生错误或无法连接的密钥库会被**记录日志并跳过**。密钥库宕机只意味着“没有命中缓存”，绝不应导致下载失败。

`Engine` 同时维护两套引用：`engine.vaults` 是实际用于查询和写入的密钥库集合，`engine.vault` 则保留为主 SQLite 兼容句柄。密钥搜索页会汇总集合中已选中的本地成员，用于 KID、标题和来源搜索。HTTP 密钥库绝不会被请求执行标题模糊搜索或来源检索；声明了搜索能力的后端只会在用户显式触发远程搜索后收到精确的 KID。

现有的两类 unshackle 密钥库均可在不做任何服务端修改的前提下直接使用；请求与响应结构完全一致，包括 `api` 后端的数值 `code` 表和 `HTTP` 后端响应体内的 `status_code`。

关于 `HTTP` 后端，有三处细节来源于实际线上服务器而非参考实现，若不专门处理就会造成静默误判：

- `status_code` 位于**响应体内部**，因此 HTTP 200 仍可能携带拒绝信息——必须以响应体为准。
- 密码被拒时返回 HTTP **401** 及纯文本消息；未知方法则返回 **400**，且错误字段名为 `error`/`type` 而非 `message`，因此上报失败原因时需要同时读取这两组字段名。
- `InsertKey` 返回 `{"status": "cached"}` 而没有 `inserted` 字段，表示服务端早已存有该密钥，同样视为成功：写入的目标本来就是确保它存有这个密钥。
