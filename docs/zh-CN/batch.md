# 批量下载

[English](../batch.md) | [简体中文](batch.md)

一次性勾选十集是一个动作，但对应十个独立结果。交付界面的顶部标题栏能描述单部作品，却无法同时描述十集；而如果串行任务全程静默、直到全部结束才给出反馈，用户根本无从监管进度。

因此，第 4 屏（交付界面）引入了任务队列。

## 自动单类型批量下载

借助通用的轨道设置，可以让批量任务只下载某一种媒体类型。将**轨道选择（Track selection）**设为 `auto`，将**输出范围（Output scope）**选为**仅视频（Video only）**、**仅音频（Audio only）**或**仅字幕（Subtitle only）**；如需保留所有命中的版本，则选择**全部匹配轨道（All matching tracks）**。**自定义（Custom）**支持以逗号分隔组合 `video`、`audio` 和 `subtitle`。默认的**普通封装（Normal package）**仍保持常规的视频/音频/字幕组合策略。

自动批量任务在各集之间绝不会弹出选轨器。如果其中某一集没有任何轨道满足完整筛选规则（例如缺少英语强制字幕），该集会被标记为**已跳过（skipped）**，其余集数继续执行。若是单标题下载，遇到同样的无匹配结果则会打开常规选轨器，供用户手动修正。

```
finished with errors  ·  1 of 2 failed  ·  ^b to go back

████████████  2 / 2 done  ·  1 failed

    1 ✓ Batch.Show.S01E01
    2 ✗ Batch.Show.S01E02  native delivery exit 1
```

## 总数如何确定

只有服务流程本身知道接下来要产出多少条播放项。驱动器通过 `on_emit` 逐条接收播放项，如果没有额外信息，它只能统计已完成的数量，却不知道总数是多少。

驱动器按优先级通过以下两种方式获知总数：

**自动推断，无需服务额外适配。** 驱动器能看到每一次交互询问的返回值。多选列表返回了六项，就意味着接下来会有六次 emit，因此 `tui/session.py:TextualPresenter.present` 会直接从返回值中读取数量并开启队列。服务无需显式声明即可自动支持。

用于翻页导航而非产出播放项的选项（例如**下一页**）必须设置 `Choice(..., navigates=True)`。驱动器在推断总数前会先剔除这类选项，防止翻页行导致队列永远等待一个不会到来的标题。

这条判断边界刻意保持得很窄，请将翻页选项与真正产出播放项的选项明确区分：

| 询问类型 | 是否推断为批量任务？ |
|---|---|
| 单选（single-select） | 否 |
| 多选但只返回 1 项 | 否 |
| 选轨器（`scope="delivery"`） | 否 |
| 多选且返回多项 | 是 |

**显式声明，用于无法自动推断的场景。** 调用 `ctx.batch(n)` 可直接告知总数。当数量并非来自多选列表时就需要它——例如服务自动采集某脚本写出的全部命令文件，中间根本不经过多选交互。显式声明会覆盖自动推断的值。

`ctx.batch()` 不像 `ctx.log()` 和 `ctx.status()` 那样“发完即忘”——它可能会抛出 `Back`，因此应将其视作一个挂起点：

```python
ctx.batch(len(content_ids))   # may raise Back
for content_id in content_ids:
    yield ctx.emit(self._playback(content_id))
```

## 任务状态

| 状态 | 符号 | 含义 |
|---|---|---|
| running | `▸` | 正在执行 |
| done | `✓` | 已下载完成，或在仅保存命令模式下已保存命令 |
| failed | `✗` | 原生交付核心返回非零退出码，或无法读取 manifest |
| skipped | `·` | 无需操作或用户跳过：未选中轨道、无 manifest URL |
| cancelled | `⊘` | 用户主动停止了当前任务及本批剩余任务 |

队列刻意不设“待开始（pending）”状态。生成器逐条送出播放项，控制器在下一个标题真正开始前并不知道它是什么，届时才会追加对应行。

每个状态同时配有专属符号与颜色，即便在不支持色彩的终端环境中也能清晰区分。

跳过不等于失败。某个标题没有可下载的 manifest 并不意味着出错，只是原生交付核心目前无法抓取它；把这类情况标红只会让用户逐渐对红色警告麻木。

## 批量确认

`confirm_batch`（默认关闭）会在做出多选的第 3 屏上针对整批任务询问一次确认——此时尚未生成具体任务，第 4 屏还没有可展示的内容。拒绝确认会抛出 `Back`，退回到你刚才进行选择的列表。

## 失败结果会保留在屏幕上

通常在流程回到服务菜单时，第 4 屏会被直接弹出——界面之间是替换关系，而非层层堆叠。但存在失败项的批量任务是例外：`8 of 10 done, 2 failed` 正是不应一闪而过、被悄悄清掉的信息，因此服务菜单会被挂载在第 4 屏*下方*，按 `^b` 关闭报告后即可露出早已就绪的菜单。

一旦用户主动关闭该页面，停留锁定就会解除；此外，发起新的批量任务也会直接覆盖上一批的报告。

## 验证方式

运行项目测试套件，并使用本地 `AutoPresenter` 或 TUI pilot 演练多选批量流程：

```bash
python -m pytest -q
```

队列应当完整记录每一条已产出的播放项，包括被取消的行。
