# 原生下载器集成

[English](../downloader-integration.md) | [简体中文](downloader-integration.md)

UniDL 的下载器是位于 Core 交付契约之后的进程内引擎。服务负责准备已授权的播放信息；Core 处理轨道选择，并将强类型的交付计划传递给下载器。无需外部下载器进程或单独检出代码仓库。

下载器实现现已内置于 `unidl` 分发包中，模块路径为 `unidl.downloader`。全新安装只包含这一个应用，不依赖外部下载器、可编辑检出仓库、外部 Python 导入或下载器子进程。生产会话通过强类型的 Core 契约完成解析与执行。同一个已安装的 `unidl` 可执行文件也提供可选的原生 `list`/`download` 媒体命令，供导出的命令使用。

账号登录、服务信息提取、CDM、许可证传输和密钥获取都不会移入下载器，这些职责仍由 UniDL 承担。内置下载器依然只接收 manifest、选中的轨道以及原始密钥。

原生实现接受公开的 `DownloadHooks`。直播 KID 轮换通过强类型请求发给宿主；UniDL 不再替换 `sys.stdin`，也不再对 `_prompt_for_live_key` 打猴子补丁。在不传入 hooks 的情况下直接调用原生 `unidl download` 命令时，仍保留原有的终端交互提示。同一个 hook 对象会在清理完成后上报最终的媒体、字幕和元数据路径，因此强类型后端不再需要自行推断成功输出的文件名。它还会发布标准化的点播（VOD）/直播轨道进度，并接受独立的取消断言（cancellation predicate）。原生传输回调和直播 manifest 等待过程都会检查该断言；取消操作不再依赖 stdout 产生输出，也不再依赖 TUI 的 ANSI 屏幕适配器收到下一帧。面板宽度由上下文局部回调提供。窗口尺寸变化会在下一次渲染时生效，无需替换模块全局变量、修改 ``COLUMNS``，也不必通过全局锁将原本独立的下载任务串行化。当 TUI 提供进度消费者时，会关闭原生引擎的控制台进度输出，改由 TUI 自行渲染这些强类型事件。独立 CLI 则因 `console_progress` 默认开启而保留现有的 ANSI 进度显示。

TUI 提供有状态的 **Pause / Resume**（暂停/恢复）控件，操作期间始终保持同一个交付任务：工作线程在分片之间或直播刷新间隔等待，当前界面保持不动，恢复（Resume）后即可继续。在活跃的点播任务中按 Back 会取消交付并返回上一页；按 Skip 仅取消当前剧目。续传可复用已校验的分片。直播录制期间按 Back 会中断下一次读取，随后基于已完成的批次收尾输出文件，再返回上一页。

通过 `ctx.session()` 发起的服务请求、Core 准备阶段以及原生交付过程，都能在取消时中断卡住的 socket 读取。自带传输层的服务应设置有限超时并提供取消机制；退出页面无法中断任意第三方同步代码。在终端应用中确认退出（Quit）后，UniDL 会给工作线程留出有限的清理时间窗口；若仍未退出，则恢复终端状态并终止进程。

多个平台配置档仍可合并为一份原生交付计划。服务通过 `Playback.merge_manifests` 启用该能力，并通过 `manifest_variants` 提供完整授权的各路变体；Core 分别解析每个请求，后端则构建一份去重后的 JSON manifest。轨道选择器、执行阶段、保存的命令以及导出功能都使用这份合并后的源，避免它们的轨道索引发生偏移。

## 目标边界

`unidl.core.delivery` 定义面向宿主的契约：

- 不可变的源、输出和计划值对象；
- 结构化的进度、日志、阶段与输出事件；
- 由执行路径检查的取消令牌（cancellation token）；
- 显式的直播密钥回调；
- 包含精确输出产物及强类型失败信息的结构化结果。

`src/unidl/downloader` 是具体实现。TUI 直接消费 Core 事件；只有后端实现才会调用下载器的内部执行 API。Core 不会拼接 argv、捕获 ANSI 输出、替换进程级标准流，或给下载器私有函数打补丁。未知的服务交付开关会在构造计划阶段直接失败，不会作为任意参数跨越边界。

## 直播重新授权

除非当前服务声明了 `LIVE_REAUTHORIZATION = True` 并实现了 [`reauthorize_live`](writing-a-service.md)，否则直播重新授权默认关闭。该功能没有全局用户开关。点播（VOD）、直播转点播（live-as-VOD）、保存的命令以及可移植导入都不会通过此机制获取新的平台会话。

- 缺少内容 KID 时，先遵循常规密钥库（Key Vault）策略。若未命中，则将当前轨道、分片及可用的初始化（init）上下文交给服务。服务返回的结果中必须包含所请求的 KID，下载器才会重试。之前被拒绝的密钥不会再次从密钥库中读取。
- 活跃 manifest 或媒体请求返回 HTTP 401/403 时，可请求新的播放源。Core 会先暂存新的轨道清单，校验所有已选轨道无误后再切换。它会丢弃旧的未提交 URL，保留已写入的批次和当前混流器，并在需要时使用新的初始化段（init section）。在遇到明确的鉴权失败后，不会继续拿着失效的媒体 URL 耗尽全部重试次数。
- 游标校验基于 HLS 的 program date-time、DASH 的呈现时间戳（presentation timing），或 Smooth Streaming 时间轴刻度除以对应轨道的 timescale。音视频可以使用不同的编号规则和分片时长。原生序列号（包括用于隐式 AES-128 IV 的 HLS 序列号）保持原样不改。缺少时间信息时，回退策略要求存在唯一的媒体重叠且序列号未发生变化。

在未取得新进展的情况下，播放源更新最多只尝试一次。如果新源存在歧义、出现断层或无法打开，所有已完整录制的批次会保存为部分录制文件，并在日志中记录原因。如果尚未录制任何内容，则录制失败。无法获取新密钥时仍提供手动输入入口；按 Back/Stop 会中断恢复流程，并在可能的情况下将此前已录制的媒体收尾保存。HTTP 404、503 或常规超时仍保持普通重试行为。

## 续传与完成文件保存

续传已选的点播（VOD）轨道时，UniDL 在恢复已完成轨道或复用已有分片之前，会先校验其初始化段（initialization section）。如果同一个 URL 现在返回了不同的初始化字节，属于该初始化段的分片会被重新下载；匹配的初始化段仍可复用。缺少可验证分片身份信息的旧缓存可能需要一次性重新下载。

对于普通 HTTP 点播，原生下载器会从正常的媒体响应中记录强 ETag。首次下载不会因此额外探测分片。重试时，在复用分片或已完成的整条轨道前，会重新核对之前记录过的资源。标记变化或无法再验证时，只重下受影响的部分。如果源站从未提供强 ETag，而且 URL、时间信息和初始化段也不变，就无法靠这个机制发现内容被原地替换。

如果在混流过程中有其他任务创建了同名的目标文件，UniDL 不会覆盖该文件，而是改用带编号的文件名发布新输出。

## VOD 播放源续期

在下载进行期间，启用了 [`VOD_REAUTHORIZATION`](writing-a-service.md) 的服务无需返回菜单即可续期已过期的有限时长播放源。原生下载器会将已选媒体播放列表、初始化段、媒体分片或 HLS 密钥请求返回的 HTTP 401/403 视为续期信号，由服务决定是否能重新授权同一资产。常规超时、HTTP 404 和 503 仍遵循普通重试策略。

在启用新播放源之前，旧传输工作线程会先停止并等待汇合（join）。Core 会校验平台的版本 ID（edition ID）、相同的已选规格（renditions）以及新宣告的 KID。已完成的既有分片和轨道检查点仅在指纹依然匹配时才会被复用；未传输完的 HTTP 响应不会带入新授权。如果新源的媒体身份无法识别，受影响的分片可能需要重新下载。若禁用了断点续传，任务会直接用新源从头开始。

只要有新的媒体位置完成下载，就可以进行多次续期。如果替换源在没有已验证进展的情况下再次过期，或者服务返回了不同版本、存在歧义/缺失的轨道，或缺少新密钥，任务就会停止而不产出混合内容，并按现有缓存策略保留可续传数据。当服务使用支持取消的客户端时，按 Back/Cancel 也会中止续期请求。

该功能与直播密钥轮换相互独立，对未配置的服务、保存的 CLI 命令、可移植导入、直播流和直播转点播均不生效。对于启用了此功能的 VOD 任务，传输由原生 Python 下载器负责，以便 Core 区分强类型 HTTP 错误并安全停止旧工作线程；其他任务的 aria2c 偏好设置不受影响。

## 脚本类 manifest URL 与请求编码

不要仅凭 URL 后缀判断响应格式。像 `getm3u8.jsp` 这类脚本端点即使不支持 HEAD 请求或服务端返回 `text/plain`，也属于 manifest 候选；在构建轨道前必须检查响应体。候选拉取失败时必须上报错误，而不能静默降级为单个视频分片。已知的直链媒体扩展名仍走原有的直连下载路径。

原生 HTTP 传输层会对路径和查询字符串中的原始空格及 UTF-8 字符进行百分号编码（percent-encode），重定向目标也同样处理。已有的百分号转义、字面加号（`+`）、重复参数和参数顺序均保持不变；绝不为了修补空格而解码并重建带签名的查询字符串。原始控制字符会在 URL 解析前被直接拒绝，而不是静默剔除。此类编码属于下载传输层职责，不会影响服务鉴权。

## 多 Period DASH 轨道

对于静态 MPD，跨连续 Period 且兼容的 Representation 会合并显示为一条连续轨道。AdaptationSet 和 Representation 的 ID 仅在所属 Period 内有效：重新编号不会拆分原本相同的轨道。语言变体、角色（role）、标签（label）、无障碍描述符、音频采样率/声道数、编码格式、分辨率与动态范围依然用于区分轨道。相同分辨率的码率阶梯按码率排序位次对齐，而不是按 XML 声明顺序；如果阶梯数量变化，或中间 Period 缺失/不兼容，则保持分离，不会静默切换画质。同一 Period 内的重复项不会被折叠合并。

静态 MPD 中省略的 Period 起始时间会根据声明的时长或相邻 Period 的起始时间推导。每个 Period 各自的初始化分片、分片时间轴和 KID 都会保留，包括明文/加密切换及密钥轮换。按已选轨道申请许可证时，会使用每个被包含 Period 对应的 ID，而不是仅靠首个 Period 的 ID 或共享 KID。轨道匹配不会引入额外的媒体探测或许可证请求。直播轨道的身份识别与刷新规则不变。

## HTTP 连接复用与自适应并发

原生 HTTP/1 连接会将每次请求的超时同时应用到连接对象和底层已有 socket 上。因此，短暂的元数据或 Range 探测不会把自己的超时期限静默遗留给后续媒体下载；调小超时同样会对复用连接立即生效。已关闭的连接池 socket 会被丢弃。

Python 下载器会在配置的 worker 预算内限制每个源站（origin）的活跃请求数。发生错误时，同一批在途（in-flight）请求不会反复叠加削减同一主机的并发度。超时、连接断开和不完整传输会采用较温和的降速幅度及短暂的有界冷却期；HTTP 429 和可重试的服务端错误则保留更强的降速与退避。如果同一批请求后续遇到服务端拒绝，允许将温和降速升级一次。降速发生前的成功响应无法取消冷却期。新的成功请求会逐步恢复并发度；若后续批次继续失败，并发度仍可一路降至 1。鉴权错误和被拒的 Range 请求不会触发主机级自适应限流。等待主机并发槽位的过程支持取消。

启用任务调试日志时，`network host=...` 日志项会记录初始上限、失败类别与计数、是否触发了新退避、活跃请求数、冷却时间以及并发恢复情况。这些记录只包含 origin，不包含签名分片路径、查询字符串、请求头、原始错误信息或密钥，也不会增加额外网络探测或控制台/TUI 消息。这是通用传输行为，并非按服务定制的限速覆盖，也不构成对 CDN 吞吐量的承诺。

## 立体视频（3D）标识

`StreamInfo.is_3d` 以及对应的 `TrackDescriptor` 标志独立于 `video_range`，用于表示显式标识的立体视频。HLS 变体通过 `REQ-VIDEO-LAYOUT`/`VIDEO-LAYOUT` 中的 `CH-STEREO`，或 `CODECS`/`SUPPLEMENTAL-CODECS` 中的 Dolby Vision Profile 20 来判定。混合的 `CH-MONO,CH-STEREO` 布局会保留 `3D` 徽标。音频声道布局、标题、URL、分辨率尺寸和帧率都不会被拿来推断 3D 属性。服务和 JSON 视频轨道也可以显式提供 `is_3d`。

轨道选择器、轨道列表、实际视频行以及进度标签都会在编码/动态范围旁显示 `3D`。原生媒体导出即使在用原始媒体播放列表快照替换主播放列表时，也会保留 `is_3d` 和 `video_layout`。该机制不增加分片表或额外媒体探测。默认发布命名模板会在动态范围之后追加 `3D`；自定义模板可使用 `{three_d?}`。这项元数据不会改变编码选择、许可证申请、解密流程、立体封装方式或混流参数。

## HLS 初始化段密钥作用域

对于整片加密的 HLS（如 AES-128），`EXT-X-MAP` 初始化段保留其声明当时生效的密钥和 IV。后续出现的 `EXT-X-KEY` 不得追溯加密此前声明的明文 MAP，在 `METHOD=NONE` 之后同样如此。在有效 AES 密钥作用域内声明的 MAP 仍按常规流程进行解密和密文校验；不得仅因响应长度不是 AES 块大小的整数倍就推断其为明文。

将尾部 CMAF MAP 与后续样本级加密元数据（SAMPLE-AES/CBCS/CENC）关联的兼容路径与整文件 AES 解密相互独立，并继续保留支持。

## 整文件条带 Blowfish 加密音频

`BF_CBC_STRIPE` 是一种传输层加密算法，而非 MP4 样本加密。JSON 音频轨道可通过 `encrypted: true` 和 `encryption_scheme: "BF_CBC_STRIPE"` 声明该方案；原生命令同样支持 `--custom-hls-method BF_CBC_STRIPE --custom-hls-key <hex-key>`。密钥长度必须为 16 字节。可选参数 `--custom-hls-iv` 长度为 8 字节，默认值为 `0001020304050607`。算法名称与原始密钥/IV 复用现有的保存命令和可移植导出字段，不涉及 CDM 或许可证交换。

该路径仅支持单个完整且非直播的媒体文件。自动分片范围下载会被禁用；显式字节范围（byte ranges）和多段输入会被直接拒绝，以避免重置条带偏移导致音频损坏。不足完整块大小的末尾短块会原样保留，不做去填充处理。使用 `--no-decrypt` 可保留原始字节。该路径在解码前会完整缓冲文件，不提供流式解密或局部续传。现有的 FLAC 文件名和 `<Ext>` 命名模式都会保留 `.flac` 后缀，即使未请求音频转码也一样。

## 混流语言元数据

平台提供的语言标签仅在构建混流元数据时进行标准化处理。`guoyu`、`putonghua` 和 `国语` 等普通话标签会映射为 `cmn`；`yueyu` 等粤语标签会映射为 `yue`。原有的旧版别名以及下划线分隔的区域标签也会一并标准化。完整的 ISO 语言、地区、文字及私有扩展标签（例如 `es-419`、`zh-Hant-HK` 和 `eng-x-51`）均予保留。无法识别的主语言代码或格式错误的标签会回退为 `und`，避免中断正常的媒体混流。

同一规则适用于已下载轨道、外部字幕/音频导入、默认轨道布局标志以及 FFmpeg 输出元数据。原始标签、轨道名称、导出的 manifest 以及自动轨道选择均不受影响；未知标签不会被猜测成其他语言。

如果 mkvmerge 根据自身的 IANA 注册表显式拒绝某个剩余标签，仅会将被拒绝的 `--language` 值替换为 `und` 后重试。其他语言标签、轨道名称、默认标志、时间戳和媒体内容保持不变。这种有界回退不会重试磁盘、编码器、输入、取消或其他混流错误，也不会切换混流器或重新下载媒体。

## MP4 加密证据与明文音频判定

加密元数据严格按实际的 ISO-BMFF box 边界解析，包括嵌套的 sample entry 和保护容器。`mdat` 内的音视频载荷字节、编码器配置记录以及未知的叶子 box 都不会被扫描用于匹配 box 名称。媒体载荷中碰巧出现的 `tenc`、`senc`、`schm` 或 `sinf` 字节绝不会凭空造出 DRM 元数据，也不会被当作真正的加密 box 去改写。

下载完成后，被标记为加密的音频轨道只有在完整的分段 MP4 给出充分证据时，才会被更正为明文：仅含一条音频轨道，具备合法的明文 sample entry，不存在保护方案或默认加密参数，且没有任何分片加密数据。更正操作会清除陈旧的轨道/分片 KID、记录日志，并跳过多余的解密步骤，不复制也不改动音频内容。判定直接基于已下载文件，不额外发起网络探测。缺少 KID、全零占位 KID、不完整的初始化数据以及不支持的布局均不能作为明文音频的证据。`--no-decrypt`、传输层加密以及真正加密的媒体仍保持原有行为。该机制不改变服务许可证逻辑或密钥库策略。

### Apple HLS 节目身份识别与音画对齐

Apple HLS 播放列表可能会将正片与片头广告（bumper）或其他资产混编在一起。本地化的视频、音频和字幕资源可能带有不同的 `P` 节目编号，但共享同一个 `A` 播放资产编号。对于托管在 Apple 上且带有显式 `mainAssetAdamId` 或单个数字 `a` 参数的点播内容，下载器会用该资产编号去匹配实际的 `P…_A…_` 媒体文件名。同一规则适用于所有已选轨道类型，并完整保留对应的初始化组（或独立的纯文本 WebVTT 分片）。查询字符串和 `_HLS_prefill` 提示不会用于识别当前媒体；资产列表绝不会通过简单取第一项来消歧。若未提供可用的 Apple 资产标识，仍沿用原有的节目 ID 规则。

对于已填充或导入的分片列表，在检查续传检查点之前同样会执行过滤。过滤后会刷新时长与体积估算；完整的分片 KID 清单会剔除仅属于被移除资产的密钥，不完整的清单则保留原有的初始化/会话级回退策略。发生变化的轨道不能复用过滤前旧音频的已完成检查点。身份匹配不引入额外的播放列表、媒体或许可证请求。带编号的分片缓存严格绑定过滤后的精确分片列表标识：旧版仅靠 URL 的回退逻辑不会错误认领分片序号已偏移的旧缓存。该检查不会修改或删除既有的源缓存。

该机制不会按时长裁剪、拉伸音频、强加人为同步延迟或改写源时间戳。属于同一资产的段落（包括本地化演职员表）会保留下来，交由下文独立的兼容性检查处理。若缺失或无法识别资产匹配结果，则保持轨道原样而不做猜测。直播录制不进行节目过滤，其他平台也不会套用 Apple 的资产 ID 解析逻辑。

### HLS 初始化段与占位 KID

选中的 HLS 轨道可能包含多个使用不同密钥的 `EXT-X-MAP` 分段，例如正片之后紧跟本地化演职员表段落。所有必需的密钥都会被保留。分段解密时，每个 MAP 对应的分片 KID 会分别传入，而不是把整条轨道的密钥列表一股脑传给每个分段。这样一来，当某个分段的 `tenc.default_KID` 为全零时，就能准确使用该分段唯一无歧义的播放列表 KID。非零初始化 KID 或显式分片 KID 不会被该回退机制覆盖。

未知或存在歧义的分段 KID 不会通过盲试第一个可用密钥来解决，原有的缺密钥报错依然生效。重试时也会基于所选分片重建映射关系，以便复用已经下载的分段。此过程不新增 manifest、媒体或许可证请求；单初始化段、DASH/ISM 以及直播录制的解密路径保持不变。

### 分段拼接兼容性与输出校验

在 MP4 分段收尾阶段，全由零字节构成的明文 `c608` 样本会被标准化为等长的 EIA-608 填充原子（padding atom）。部分源站用全零样本作为空白字幕占位，而 FFmpeg 的 concat 读取器即使在只选了视频轨时也会直接拒收它们。修改前会校验轨道/样本边界以及媒体数据边界。合法字幕、受保护条目以及所有音视频载荷均保持原样；任意损坏的字幕不会被静默忽略。

对于非直播的 Apple HLS 视频，尾部显式命名为同一资产下 `FF_credit-` 资源的段落可能包含不兼容的可选演职员表渲染版本。下载完成后，系统会将实际的初始化数据与正片的编码格式、编码尺寸及可用的色彩声明进行比对。只有确认不兼容的演职员表分段才会被剔除，并在日志中记录剔除数量和时长。兼容或未知分段、普通正片分段、其他资产/平台以及直播流都会保留。判定不会根据 KID 或 discontinuity 臆断不兼容，也不会对视频转码、改动缓存源文件，或发起额外的网络/许可证请求。

FFmpeg concat 启用致命错误处理模式，并且在进程意外返回退出码 0 但输出明确解复用错误时同样判定失败。拼接结果会先写入临时文件，成功后再正式发布；半成品或空输出会被清除，且不会覆盖已有的完成文件。

### 有界内存 MP4 元数据编辑

时间戳/分段收尾以及本地时间/KID 探测不再把整个媒体文件读入 Python 字节缓冲区。探测使用只读文件映射并跳过媒体载荷 box。编辑阶段仅保留发生改动的 4 KiB 内存页；发布时以 8 MiB 分块流式读取源文件，并将这些元数据页应用到原子临时输出中。这既避免了与文件等大的 Python 内存拷贝，也避免了 Windows 上与文件等大的写时复制（copy-on-write）映射预留。工作内存仍取决于元数据复杂度，操作系统文件缓存另计。

时间计算、媒体字节和空白字幕标准化逻辑保持不变。编辑失败时，源文件、已有目标文件以及关联检查点均完好无损。未产生改动的原地编辑不会复制文件。这只是内存优化，不改变临时文件保留策略、许可证/解密策略、混流器选择或暂存分段数量。

检查点目录统计的总大小可能会将指向同一份媒体数据的多个硬链接名重复计入。评估磁盘占用时应比较实际分配空间或去重后的唯一文件空间，而不仅是文件大小之和。调试/`keep_temp` 模式还可能保留早期的加密和明文版本；这些属于磁盘文件，并非对应体量的常驻内存占用。

## BBTS 下载后处理性能

BBTS 解密采用原生字节搜索与防竞争校验字节（emulation-byte）移除、有界的 64 KiB 计数器掩码批次、批量 AES 以及原生 XOR 运算。使用 `cryptography` 回退方案的环境无需新增依赖即可保持完全一致的字节输出。稀疏 AES 调度、末块规则、NAL 边界以及原始尾部处理均保持不变。

重建后的相邻 TS 包按每批最多 4096 个包写入；包含音频或其他 PID 的间隙绝不会被覆盖。明文前导段和按 PES 切换密钥仍保持既有行为。该优化仅加速 BBTS 后处理，不新增网络或许可证请求，不改变下载工作线程数，也不修改其他解密路径。

## 独立压缩的 MP4 初始化段

源站可能会独立于媒体分片对 MP4 初始化资源启用 gzip 压缩。拼装阶段，UniDL 只会解压经过校验、且包含完整 `ftyp`/`moov` 初始化 box 的 gzip 成员；后续媒体字节原样拷贝。原始传输分片保持不变，供续传和体积校验使用。同样的标准化处理也适用于多初始化段输出以及 Python/aria2 拼装路径。

先前已完成但带有此类压缩前缀的轨道会在混流前被标准化为临时混流输入，因此重试失败的混流无需重新下载音频。原文件、语言/默认标志以及其他元数据均予保留；临时文件在成功或失败后都会清理。解压过程受大小边界限制，截断或损坏的 gzip 会被直接拒绝；该机制不会放宽混流错误检查，也不改变常规的内嵌与独立音频选择策略。

## 服务暂存的 XML 字幕

放入 `Playback.mux_imports` 的外部字幕文件会绕过已下载轨道的常规转换流程。因此，共享的混流准备阶段会在交给 FFmpeg 或 mkvmerge 之前，先使用 UniDL 的原生字幕转换器将 `.xml`、`.ttml` 和 `.dfxp` 输入转为临时 SRT 文件。在可选的 `subby` 辅助工具缺失或失败时，这同样覆盖 BBC EBU-TT/IMSC 字幕。

原始 XML 文件保持不动；时间轴、文本、语言、名称、disposition 标志和延迟都会保留。SRT 无法保留 TTML 样式或屏幕定位。转换采用按任务生成的短文件名，避免在 Windows 路径中反复拼接过长的发布名称。无论成功、准备失败、取消还是混流失败，临时文件都会被清理。无效字幕会以字幕准备错误失败，而不会被静默丢弃；已下载的媒体文件仍然保留。现有的 SRT/VTT 以及音视频输入仍走原有路径。

## ASS/SSA 字幕输入

服务自有 API 的字幕准备阶段会在原生媒体传输之前纳入共享下载框架。Core 直接观察选中的外挂（sidecar）轨道行及其准备好的文件，不会去解析服务日志文本来伪造进度百分比。旧版钩子保持原有的传输与转换行为，在文件准备成功前显示活跃/未知进度状态。服务也可以实现 `prepare_download_with_progress(playback, log, progress)`，并调用 `progress(reference, received_bytes, total_bytes)` 上报实测字节进度；总大小未知时传入 `None`。Core 仅在文件实际存在且已加入 `Playback.mux_imports` 后才发布完成状态。每条导入项应保留语言、名称、类型以及 forced/original 标志，确保同语言的多条轨道仍可区分。已完成的字幕行在移交至原生音视频进度阶段后依然保留显示。命令、列表和导出模式不会下载外挂字幕。

ASS/SSA 轨道保留其原始输入扩展名，包括仅声明编码格式的 JSON 轨道。基于内容的识别机制能正确处理被误标为 TTML 或 WebVTT 的 ASS/SSA 文本，同时不会把长得像文件头的对白误判为脚本。已识别的空白字幕文档不会触发 FFmpeg 转换警告。关于转换逻辑、纯文本时间轴修复及样式保留详情，请参阅 [ASS/SSA 字幕输入](downloader/ass-subtitles.md)。

## 服务按需启用的混流音视频投影

`Playback.split_muxed_audio` 默认关闭（false）。服务可针对明文或 AES-128 点播显式启用该项，从而在轨道选择前无需拉取媒体或初始化字节，即可暴露独立的视频与音频条目。原生后端会在 manifest-source JSON 中保留原始源配置并写入 `split_muxed_audio: true`，在不展开分片数组的前提下完整支持主/媒体播放列表导出和命令重放。服务过滤器会在投影前对原始轨道打标，源站标识与输出过滤器标识会同步传递给派生出的两条轨道。

下载器在同一任务内共享每个物理源，随后合并、解密并无损抽取选中的首条视频流或首条音频流。每个输出都有独立的持久化检查点。抽取失败时会保留已完成的源检查点供重试；等待共享源的过程仍支持取消。FFmpeg 由现有下载运行时管理。默认服务、无关轨道、旧版续传标识以及直播录制均不受影响。该初版分离契约暂不支持样本级加密（CENC/CBCS/SAMPLE-AES）源，对这类源启用会明确报错。

## VOD 临时磁盘占用

当一条完整轨道拼装完成后，常规清理会在整文件解密前删除多余的下载分片，但前提是后续处理不再需要它们。启用断点续传时，系统会先校验拼装好的轨道，并在删除分片前原子性地将检查点更新为不再依赖这些分片。因此，解密失败时可直接基于拼装结果重试，无需重新下载；重试旧版已下载检查点时也会以同样方式精简空间。分片级解密和直播录制会保留所需输入文件。`keep_temp` 或关闭自动清理时，仍按配置保留文件。

对于包含多个 `EXT-X-MAP` 分段的有限时长 HLS fMP4，常规 Python/aria2 下载会直接按分段拼装，不再多复制一份整轨副本。Core 会在删除多余分片前发布带指纹的纯分段检查点；重试时会自动迁移旧版整轨检查点。在不支持硬链接的文件系统上，借助极小的代际标记（generation marker）避免复制首个分段。解密或拼接失败后，可直接从完好的源分段恢复，无需重新下载。

明文解密与时间戳修正的工作副本位于私有临时作用域内。时间戳修正会原子替换每个生成的明文分段，而不是额外保留第二套完整文件。无论成功、失败还是取消，该临时作用域都会被清理；源分段则保留至完整的明文轨道检查点发布完成。单分段结果会直接移动到位，拼接前也会检查可用磁盘空间。密钥作用域、字幕/时间修正、媒体字节、显式保留设置和直播录制行为均无变化。

在同一本地文件系统且启用常规清理的情况下，这套多段 HLS 路径在解密与分段拼接阶段大约需要预留所选媒体体积 3 倍的空间外加余量，到最终混流阶段则约为 2 倍。这只是峰值预算参考，不代表启用调试保留或额外后处理时的上限。

对于单轨单 KID 的常规加密 DASH 点播，在支持硬链接的同一本地文件系统并启用常规清理时，主要峰值大约为所选媒体体积的 2 倍加安全余量：即“分片 + 拼装文件”、“加密轨 + 明文轨”，或“明文轨 + 混流输出”。这并非适用于所有场景的硬性存储上限；调试/保留设置、重新封装、音频转码、混合处理、不支持硬链接的文件系统以及跨文件系统拷贝都可能消耗更多空间。请同时检查临时目录所在文件系统和最终目标目录的剩余空间，因为混流文件会先暂存，确认无误后再提交至下载目录。

## MP4Box 与 3D 输出

在 **Download behavior → Muxer** 中新增了 `MP4Box (MP4)` 选项，对应的 CLI 参数为 `--muxer mp4box`。它同样可以混流普通视频、音频和字幕输入，并固定输出 MP4 容器/后缀。请安装 GPAC/MP4Box，并将 `MP4Box`（或 `mp4box`）加入 `PATH`；本地输入轨道由 FFprobe 识别。依赖检查界面会将缺失的 MP4Box 列为可选能力并提供安装指引。需要用到它的 VOD 任务如果发现缺失，会在下载媒体前直接报错，不会静默回退到 FFmpeg 或 mkvmerge。独立的 VTT/ASS/TTML 字幕会先转为 SRT，再以 tx3g 格式封装进 MP4 以保证播放兼容性；源文件和 No mux 输出不受影响。

选中 3D 点播轨道时，系统会自动选用 MP4 + MP4Box，覆盖常规容器和混流器设置；No mux 仍拥有更高优先级。直播 FIFO 录制仍继续使用 FFmpeg。该模式保留原生 MV-HEVC，而非将其转换为左右分屏（side-by-side）视频；播放需要支持立体/MV-HEVC 的播放器与设备。

对于多初始化段的分段 MP4 立体视频，Core 会把每个分段原有的 sample description（包括穿插的 2D 单目片段）完整保留在同一个初始化段中，并显式重映射分片描述索引与相对数据偏移。在现有的解密和时间轴修正完成后，媒体载荷字节原样流式输出。不支持的布局会明确报错，而不是丢掉一只眼睛的画面或凭空生成多余视频轨。最终 MP4Box ISO 导入使用 `-new -flat` 参数：GPAC 2.x 的流式 `-newfs` 导入器可能会丢弃未知的立体视频 box，而 `-cat` 则可能把混合 sample description 拆成多条视频轨。

最终混流会在发布输出前校验关联的 `hvcC/lhvC/vexu/dvcC/dvvC` 配置是否与立体视频源条目一致。如果旧的已完成轨道检查点缺失立体元数据，需要重新构建该轨道，单纯修改输出文件扩展名无法恢复。原始输入文件不会被修改。flat 写入方式避免了生成与视频等大的交错临时文件，但会把元数据放在媒体数据末尾，而非生成 fast-start MP4。

## 迁移验收标准

1. 单个 UniDL 分发包同时包含服务层与下载引擎；不再安装或导入第二个下载器包。
2. 强类型后端无需调用方构造 argv 即可完成解析与执行。
3. 进度、最终路径、错误和直播密钥请求均为结构化事件。
4. 取消状态在网络/下载工作线程内检查，而不是等到下一次打印输出时才检查。
5. 已知的服务交付开关解码为强类型计划字段；未知开关在计划构造阶段直接失败，不跨越边界。
6. Core 中已移除面向 ANSI/stdin/私有函数的兼容垫片。
7. 在原有独立检出仓库退役前，VOD、纯音频、JSON、HLS、DASH、ISM、直播、SABR、VGC 及特殊 HLS 的一致性测试全部通过。
