# 直播频道

[English](../live.md) | [简体中文](live.md)

直播流是这里唯一不会自行结束的任务，下面所有设计都源于这一事实。

## 选轨后确认录制

主界面上的 `live_record` 是持久化默认值，决定遇到直播频道时是*录制*还是仅*解析*。在交互式 TUI 中，系统会在最终轨道选定之后、启动录制器之前向用户确认：

| `live_record` | 对直播频道的默认处理 |
|---|---|
| 关（默认） | 预选 **Save the command only**（仅保存命令） |
| 开 | 预选 **Record it now**（立即录制） |

用户可以在当次运行中更改该选择，且不会覆盖已保存的默认值。在无头（headless）运行模式下，已保存的配置值直接生效。默认关闭是因为两种误操作的代价不对称：误开的直播录制会持续写满磁盘并在时长上限内占用会话，而未启动的录制只需按一次键就能重新开始。交付界面会明确提示实际执行了哪一项，而不是静默无动作：

```
live     not recording, saving the command instead
!  live recording was not selected; saving the command
```

## 录制时长按服务配置

`live_record_limit` 位于每个服务各自的设置中作为默认值，因为录制时长取决于录制内容本身：足球赛、滚动新闻频道与电台需要三个完全不同的时长。最终轨道确定且选择 **Record it now**（立即录制）后，TUI 仅在用户选择 **Record from the live edge**（从直播前沿录制）时询问本次录制时长。回看（DVR）选项的有限区间直接来源于检测到的窗口，而“从窗口起点开始并持续录制直播”则保持无上限直至手动停止。临时修改不会改写服务保存的默认值。时长输入支持 `HH:MM:SS`、纯秒数或 `1h20m`——凡是原生下载器支持的格式均可接受。输入框默认显示 `00:00:00`，表示**无时长限制**：持续录制直至用户按下 Stop、Back 或 Esc。非零值则用于无人值守或无头录制时的显式安全上限。

Back（返回）操作在该交互链路中逐级回退：在时长输入框返回到直播前沿/回看来源选择；在回看检测阶段返回到该来源选择；在回看模式选择界面返回到来源选择；在偏移量输入框返回到回看模式选择。如果在最初的“录制还是仅保存命令”选择界面按 Back，且启用了交互式选轨，则会回到上一步的选轨器。

只有声明了 `SUPPORTS_LIVE` 的服务才会暴露直播设置。如果给没有直播频道的服务放一个录制时长选项，只会制造一个可改却永远不会被读取的无效配置。

## 回看窗口

大多数直播 manifest 公布的都不只是当前直播前沿，还包含一段可回溯的近期历史——即回看（DVR）窗口。`live_replay`（按服务配置，默认关闭）决定了选轨后的确认步骤默认停留在直播前沿，还是先提示检测回看窗口。

关闭时，默认预选 **Record from the live edge**（从直播前沿录制）。只有该路径会询问录制时长，`00:00:00` 表示无时长限制。

开启时，默认预选 **Detect the live replay / DVR window**（检测直播回看 / DVR 窗口）。只有在用户明确选择此项后，UniDL 才会拉取所选媒体播放列表以测量窗口长度；若检测到可用窗口，交付界面只提供以下三个选项：

| 选项 | 原生下载器参数 | 结束条件 |
|---|---|---|
| 录制当前整个回看窗口 | `--live-perform-as-vod` | 接近当前直播前沿 |
| 从窗口起点开始并持续录制直播 | `--live-dvr-from-start` | 用户手动停止 |
| 录制窗口内的指定区间 | `--live-dvr-start-at`、`--live-dvr-end-at` | 到达结束偏移量 |

第一项和第三项都是有限区间，因此不会再叠加录制时长上限；第二项从测得的窗口起点开始，一直录过直播前沿直到手动停止。指定区间在单个输入框内填写：例如对于一小时的窗口，`00:15:00-00:40:00` 表示从窗口起点起算的 15 分钟到 40 分钟（即直播前沿前 45 分钟到前 20 分钟）。如果输入无法解析，系统会明确提示并从回看窗口起点开始，而不会把无效值往下传。

### 为什么作为交互选项而不是固定设置

回看窗口有多长取决于打开流那一刻的实时状态，而非服务本身的属性。32 秒缓冲区和 6 小时回看窗口在协议上都是“直播”，但实际有意义的选择截然不同。因此配置项只保存默认偏好，真正的选择会在拿到 manifest 并选定最终轨道之后再询问用户。

测量回看窗口需要额外做一次解析。常规解析只停在主播放列表（选轨器所需信息均在其中），不拉取子播放列表就无从得知窗口长度，甚至不知道流是不是直播：`is_live` 会返回 `False`，`duration` 也为空。因此测量只在结果即将被用到、且用户明确选择检测回看时才触发。短于两分钟的范围视为常规缓冲而非回看窗口：例如 BBC 直播电台仅公布 32 秒缓冲，而广播电视平台的回看窗口通常以小时计。

## 实时 MKV 与内嵌 AAC

对于包含内嵌 AAC 的 HLS TS 输入（包括 URL 不带文件扩展名的媒体流），实时管道混流仍然保持启用。面对此类输入，UniDL 会省略 FFmpeg Matroska 封装器的 `-live 1` 标志，以便首批音频包提供 AAC 配置信息，并让混流器得以更新输出文件头。此举不会退回成“先分轨录制、结束后再整体重封装”。

输出依然是下载目录中持续增长、立即可见的文件，保持 1 秒 / 64 KiB 簇上限与及时刷盘。正常停止会关闭录制并写入文件尾与索引。音视频均直接流拷贝而不转码；fMP4、其他输入类型以及 Back/Quit 行为保持不变。

## 验证方法

使用不带 `ENDLIST` 的本地播放列表或确定性的模拟刷新循环，然后运行项目测试套件：

```bash
python -m pytest -q
```

直播测试夹具应仅放在本地并完成脱敏。严禁提交凭据、带签名的 manifest 或内容密钥。
